Report. Measured 2026-08-27. Report before building, so nothing below is

## 1. THE WEEKLY CYCLE, IN ORDER

Twelve steps from capture to a file in someone's inbox.

     1  capture the government lane
     2  capture the Serper, opportunity, fuel, feasibility and TED lanes
     3  re-cluster, because government feeds the clusterer the Serper half
     4  record what each source actually captured
     5  judge it: is any market silent, is any feed dead
     6  decide which clients are due this week
     7  build each due client's document
     8  render it, and refuse it if provenance is incomplete
     9  record the delivery
    10  put the file somewhere the recipient can reach
    11  tell the recipient it is there
    12  raise an alarm if any of 1 to 11 went wrong

Steps 1 to 5 are the corpus. 6 to 9 are the document. 10 to 12 are the product,
and they are the three that do not exist.

## 3. WHAT DECIDES WHICH CLIENTS GET A DOCUMENT

**Today, nothing does, and a strict reading of the model produces zero
documents on any Monday.**

The model is already there. Migration 025 line 39 says it in as many words:
"CADENCE AND NEXT_DELIVERY are what a scheduled agent will later read." This is
that agent, and the fields are waiting. They are set and displayed on
`clients/page.tsx` and `client/[id]/page.tsx`, and read by nothing.

Both clients, in full:

    JKR & Associates     status=active   cadence=monthly   next_delivery=null   brand=JKR & Associates
    Simtec Attractions   status=active   cadence=monthly   next_delivery=null   brand=null

So three separate facts block step 6, and only one of them is code:

1. `next_delivery` is null on both, so nothing is ever due.
2. `cadence` is `monthly` on both, and the product being designed is weekly.
3. Nothing reads either column.

There is a second gate underneath, and it is working correctly.
`client_projects` decides what a client may be shown at all: **120 included, 383
proposed, 10 excluded, 513 total.** A client with no included rows has nothing
to send even in a busy week, and that is the membership gate doing its job
rather than a fault.

**The rule I would propose for step 6,** stated here and not built until
confirmed: a client is due when `status = 'active'` AND `next_delivery <= today`.
On generation, `next_delivery` advances by the cadence. A null `next_delivery`
means never due rather than always due, because the failure mode of the other
reading is mailing every client every week from a single missing value.

## 4. WHAT A WEEK WITH NOTHING TO REPORT SHOULD SEND

**It should send the document, with the zero stated.** Not silence, and not a
different shorter artefact.

Silence is indistinguishable from the system being dead, which is precisely the
failure standing rule 3 exists to prevent and precisely what Brief S item 1C
says about the register: a dead source looks like a quiet week. If a quiet week
and a broken pipeline produce the same empty inbox, the client cannot tell which
one they are paying for.

So a nothing week sends a document that carries:

- the scope it searched, in the client's own terms;
- the period, and the explicit count zero;
- every market read, and for each one the date of its last successful capture;
- anything withheld, with the count and the reason, per standing rule 3;
- and the coverage note naming any market that was silent this run.

That last line is exactly what `lib/source-health.ts` was written to produce and
exactly what migration 044 is blocking. A quiet week is the week that most needs
the health sentence, because it is the week where "we found nothing" and "we
looked at nothing" are the two possible meanings and only one of them is
acceptable.

A quiet week is also the cheapest possible proof that the system ran. It is a
feature of the product, not an embarrassment to be suppressed.

## 5. WHERE AN ALARM LANDS WHEN NOBODY IS WATCHING

Today it lands in stdout, and on a runner that is a log file nobody opens.

The hard part is not the transport. It is that **a run which captures nothing
still exits 0.** `HEALTH_NO_WRITE=1` is one environment variable away from a run
that looks completely normal and records nothing, and CLAUDE.md already says so.
An alarm attached only to a crash will never fire for the failure this system
actually has.

| Where it could land | Cost | Fires on a crash | Fires on a silent capture | New auth |
|---|---|---|---|---|
| Job failure, GitHub's own email | $0 | yes | only if the job exits non-zero on the verdict | none |
| A GitHub Issue, opened or updated | $0 | yes | yes | none, `GITHUB_TOKEN` |
| Email via the existing Gmail route | $0 | yes | yes | `credentials.json` and `token.json` as CI secrets |
| Slack or a push service | $0 to ~$8/mo | yes | yes | a new webhook and a new account |
| A paid monitor, Sentry or similar | ~$26/mo | yes | no, it is not an error | an account |

**Recommendation: the second, plus the first.** The repository already proves the
pattern: `.github/workflows/manual-portal-check.yml` opens and updates a weekly
GitHub Issue from the built-in `GITHUB_TOKEN`, with zero new auth, and its own
header explains that this is the zero-dependency channel precisely because it
needs no Gmail send scope. The weekly run should write its verdict into an issue
the same way, and a red verdict should ALSO fail the job so that GitHub's own
failure mail fires without anything being built for it.

The paid monitor is ruled out on fit rather than on price: a market going silent
is not an exception, so an exception tracker will never see it.

## 6. THE SMALLEST VERSION THAT COULD RUN NEXT MONDAY

Not the complete one. A cadence that runs badly and gets fixed beats a perfect
one that never ships.

**Host: GitHub Actions, `ubuntu-latest`.** Not a guess. This repository already
runs a scheduled workflow there. Every Windows trap in CLAUDE.md is a Windows
trap: the OneDrive `.next` lock, the `EINVAL: readlink`, the server that must be
killed before a build. A Linux runner meets none of them, and that is a reason to
move rather than a convenience.

**One workflow, `weekly.yml`, Monday 01:00 UTC, which is 08:00 Bangkok.**

    1  checkout, node, npm ci
    2  npm run scrape:government          government first, it feeds the clusterer
    3  npm run scrape:all                 the Serper half, then the re-run
    4  npm run verify:staleness           and the health verdict
    5  build the dashboard, start it on :3000
    6  Playwright generates each due client's document, reusing report.shots.ts
    7  upload the PDFs as workflow artefacts
    8  open or update a GitHub Issue: counts, per-market capture state, artefact link
    9  exit non-zero if the health verdict is red

**Why step 6 is Playwright and not a new generator.** It is the smaller change by
a wide margin. `buildReport` is behind `'use client'` and extracting it is real
work that has to respect the package split, which is asymmetric and has broken a
deploy once already. `report.shots.ts` already generates three real documents by
driving the same buttons a person drives, already routes its output through
`e2e/artefacts.ts`, and already runs headless. Reusing it means the first Monday
document is built by the exact code path Philip uses, which is also the only way
to be sure it is the same document.

It is not the right long-term answer. It is the right first one.

**Delivery in v1 is a workflow artefact plus an issue, not an email.** GitHub
mails you when an issue is opened on a repository you watch, so a document does
arrive without anyone generating it, which is the test. Wiring the Gmail route
means putting `token.json` into CI secrets and touching the send path, and that
is v2 work with standing rule 12 sitting next to it.

**Four secrets.** `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
`SUPABASE_SERVICE_ROLE_KEY`, `ANTHROPIC_API_KEY`. `SERPER_API_KEY` makes five if
the Serper lane runs on the first Monday; it can be left out of v1 and the
government lane run alone, which is the half that feeds covered markets anyway.

on a private repository and is unlimited on a public one, so the cost question is
whether a full cycle fits in an hour, not whether it fits in a budget.
