# BRIEF S. DELIVERY.

Write this file to the repo before starting.

This is the last brief. After it the system runs weekly without anyone
triggering it and a document arrives without anyone generating it.

Everything before this made the corpus honest. This makes it arrive.

## Standing rules

Measure before you build. A rule ships with the count behind it and the cost
per market stated. Report before you propose. Read the body, not the status
code. Never fabricate. Nothing is silently absent. Sweep for the shape before
the fix is committed. State the cap beside any figure taken from a capped read.
NPM_EXIT from the captured line on every gate. Migrations are printed, never
run from code.

## ITEM 1. THE THREE DEFECTS THAT REACH A CLIENT

These come first because each one can put a wrong document in front of someone.

**A. The sticky brand override.** `brandOverride` and `addresseeOverride` are
never cleared when the client selector changes. Type an override with JKR
selected, switch to Simtec, generate, and the Simtec document goes out branded
JKR & Associates. Simtec carries null brand and null addressee, so its correct
output is exactly what a stale override replaces. The on-screen hint says
selecting a client loads their stored brand and that overriding changes this
report only. Both sentences are false for a typed override.

Fix it, and assert it: a client change clears every override, and a document's
brand and addressee match the selected client unless an override was typed
after the selection.

**B. The date-only filename.** `${who}-${what}-${stamp}` with a date-only
stamp. Two market reports for one client on one day produce one `file_path`,
and `deliveries` holds 1,447 rows whose whole purpose is to answer what a client
received. Report what collides today before fixing it.

**C. The register is silent when a source dies.** The run alarms and a document
states its exclusions, and nothing on the projects screen reads `source_health`
or `dead-feeds`. A dead source looks like a quiet week.

Surface it. Report first what the screen would have to read and where it goes,
then build. It is my working surface, so a banner I can ignore is worse than
nothing.

**D. And the hollow stage, which is the same family as C.** 71 projects hold
zero records and carry a live stage, 69 of them hearing scheduled. Nothing
recomputes a stage when the last record leaves. Report the rule: what should a
project with no live records read as, and does anything print it today.

## ITEM 2. HEALTH-GATED GENERATION

A document must not ship from a corpus that did not capture.

Report first: what the run already records per source, what a generation reads
today, and what it would take for a generation to refuse.

Then propose the rule. My starting position, argue against it if the numbers
say otherwise: a document generated when a market's feed failed on the last run
states that in the coverage note with the market named and the date of the last
successful capture. It does not refuse. A stated gap is the product; a refusal
is an outage.

---

## ITEM 3. HOSTED CAPTURE

The runs happen because someone types a command.

Report what it would take to run the capture on a schedule without this
machine: which commands make up a full cycle, what each needs from the
environment, what the wall time and cost are, and where they could run. Vercel
cron, a GitHub action, and a small always-on host are the obvious three.

State plainly what breaks when nobody is watching: the Windows-specific traps
in CLAUDE.md, the OneDrive lock, the server-must-be-killed-before-build rule.
Those are local defects and a hosted run should not inherit them.

Report before proposing. Do not build it.

---

## ITEM 4. THE EGRESS DECISION

One decision unblocks four sources: Las Vegas behind Cloudflare, Anaheim's
Granicus, San Antonio's PrimeGov, and Mexico's SEMARNAT. It has been logged for
weeks and never costed.

Report: what each of the four actually refuses today, whether it is IP-based or
header-based, and what egress would satisfy all four. Then the options with
costs.

Measure before recommending. A source that 403s to a data centre may answer a
residential egress, or may need a session, and those are different problems
with different prices.

---

## ITEM 5. THE CADENCE

The product is a document that arrives.

Report before building: what a weekly cycle would consist of, in order, from
capture to a file in someone's inbox. Where each step already exists and where
it does not. What decides which clients get a document in a given week, and
what a week with nothing to report should send.

Then propose the smallest version that could run next Monday. Not the complete
one.
